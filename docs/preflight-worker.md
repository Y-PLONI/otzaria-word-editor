# עיבוד חבילת המסמך ב־worker

## החוזה

- `preflightSource` נשארת נקודת הכניסה. קריאת המקור, שמירת ה־Blob, התקנת גופנים וחיבור לעורך נשארים בתהליכון הראשי.
- `preflightPackage` ב־`docx-preflight-core.ts` מריצה את עיבוד ZIP/XML/VBA הקיים: ספריית ZIP משותפת, סדר תיקונים, CRC, תיקוני כתב מורכב ומיזוג ריצות לא השתנו.
- ה־worker מחזיר בייטים מתוקנים או `null` שמשמעותו „השתמש ב־Blob המקורי”, טבלת גופנים, מידע VBA והודעות. חלקים שלא תוקנו אינם נכתבים מחדש.
- כל `ArrayBuffer` נמסר עם transfer list. מקור URL נקרא ל־Blob פעם אחת; תוצאה ללא תיקון אינה מעבירה את כל הקובץ בחזרה. ה־Blob אינו מועבר ונשאר זמין להתאוששות.

## בעלות, ביטול וכשל

`LoadAttempt.signal` מבוטל ב„דלג”, החלפת פתיחה, כשל או פירוק המעטפת. קריאת URL מקבלת את אותו signal. לכל בקשה worker נפרד ומזהה ייחודי; ביטול מסיים אותו בלי להשפיע על מסמך אחר. הצלחה וכשל מסיימים אותו גם הם. תגובה עם מזהה או פעולה אחרים אינה מתקבלת. בדיקות הביטול הקיימות במעטפת נשארות לפני שינוי מצב המסמך.

גוף העורך הקודם מקבל `inert` בזמן הפתיחה: אחרת placeholder נקי יכול לקבל הקלדה שתימחק כשיחליפו אותו. החסימה שייכת ל־container שנלכד, ושומרת את מצב ה־`inert` המקורי. ביטול משחרר אותה מיד; `finally` מאוחר אינו משחרר ניסיון חדש. ה־stack והמועמד החדש נשארים זמינים למיקוד ולשחזור הסמן. אין החזרת focus יזומה לעורך הישן.

`inert` אינו חוסם מאזיני `window`: בפרוב, Ctrl+B ו־Ctrl+Enter מה־body עדיין שינו את העורך הישן. לכן מנתב הקיצורים והמאזין הנפרד לכיווניות בודקים את ה־container הפעיל בזמן האירוע. פקודות, פעולות עריכה וקיצורים אישיים נחסמים כל עוד אותו עורך נעול; Escape, עזרת קיצורים, F6/Tab והקלדה בשדות UI נשארים זמינים. מעגל F6 מדלג על העורך הנעול. העורך החדש והעורך שנשאר לאחר ביטול מקבלים שוב קיצורים.

Tell Me שכבר נפתח בודק את אותה נעילה לפני ביצוע פעולה. דיאלוג המאקרו שומר את הטופס אך חוסם ניגון, הכנסת קטע, הרצת סקריפט והרצת כלי בזמן הפתיחה; גם שם יש בדיקה בזמן הלחיצה, לפני עדכון רינדור. החסימה מונעת התחלת פעולות אלו ואינה מבטלת מאקרו שכבר רץ.

לאחר כשל worker מתבצע ניסיון מקומי אחד עם אותו core. זה משמר את מדיניות „לתקן, ולא לחסום”, ובפרט אינו מדלג על ההגנה מפני `defaultTabStop=0`. אם הבייטים כבר הועברו, קוראים מחדש את ה־Blob השמור; אין הורדה חוזרת. אם ההעברה כלל לא התבצעה, משתמשים ב־buffer שכבר נקרא. כשל בעיבוד עצמו ממשיך להחזיר את המקור כמקודם. ביטול אינו מפעיל את ההתאוששות.

**ההתאוששות המקומית עלולה לחסום את הממשק.** היא מסלול חריג, ומדידת worker אינה נחשבת תקינה אם נאלצה להשתמש בו. קריאת Blob ועיבוד מקומי שכבר התחילו אינם ניתנים לקטיעה באמצע; תוצאת פתיחה מבוטלת נזרקת.

הפרוטוקול המשותף נמצא ב־`docx-package-protocol.ts`: גרסה, מזהה בקשה, פעולה ובייטים. הוספת postflight דורשת תוצאה ו־validator ב־`PackageResults` וב־`validators`, וענף ב־dispatcher של ה־worker; אין צורך לשנות את מנהל ההעברה או ליצור תור שמערבב מסמכים.

## `file://` ואריזה

`?worker&inline` משתמש ב־`worker.format: 'iife'` שכבר מוגדר ב־Vite. באריזה נוצר worker קלאסי מ־Blob URL; אין module worker, `fetch(file://...)`, נכס רשת חדש או שינוי ב־workers של SuperDoc. מקור worker החבילה כלול בבאנדל של האפליקציה. בפיתוח Vite מנהל את כתובת ה־worker שלו כרגיל.

## אימות ומדידה

```sh
npm test -- tests/unit/docx-package-worker.test.ts tests/unit/docx-preflight.test.ts tests/unit/document-load.test.ts tests/unit/vba-document.test.ts --maxWorkers=1
npm test -- tests/component/app-shell.test.ts tests/component/macros-dialog.test.ts tests/unit/shortcut-dispatch.test.ts --maxWorkers=1
npm run typecheck
npm run build
npm run check:dist
CHROME=/path/to/chrome npm run check:preflight-worker -- --out /tmp/preflight.json
CHROME=/path/to/chrome npm run check:preflight-worker -- --package-only --cpu 4 --out /tmp/preflight-cpu4.json
CHROME=/path/to/chrome node scripts/qa/preflight-interaction-qa.mjs --out /tmp/preflight-interaction.json
```

שער הדפדפן בונה entry לבדיקות מאותו מקור ומאותה הגדרת IIFE, ופותח אותו ב־`file://` אמיתי. הוא משווה SHA-256 ומידע נלווה בין עיבוד מקומי ל־worker בארכיון ללא תיקון, XML גדול דחוס, ארכיון פגום וחבילות עם VBA. החבילות כוללות פרויקט VBA אמיתי של Office בתוך DOCM מינימלי, גם לצד XML שמצריך תיקון; פרויקט סינתטי עם `AutoOpen`, טקסט בעברית ואזהרה; וחלק VBA פגום. נבדקים שימור המודולים, המקור, ההודעות ובייטי ה־VBA, transfer אמיתי, ביטול וסיום worker. המקור והרישיונות נמצאים ב־`tests/fixtures/preflight/UPSTREAM-NOTICE.md`. VBA אינו מורץ.

שלושת המדדים מדווחים בנפרד:

| מדד | תחום המדידה |
| --- | --- |
| `wallMs` | קריאת ה־Blob, עיבוד החבילה והכנת תוצאת הפתיחה; כולל הקמת worker והודעות |
| `longestTaskMs` / `mainBlockingMs` | משימות התהליכון הראשי בזמן עיבוד החבילה; blocking הוא סכום החלק שמעבר ל־50 מ״ש בכל long task |
| `sourceToSettledDocumentMs` | ב־dist האמיתי: תחילת קריאת המקור עד סיום מחוון הפתיחה והופעת תוכן המסמך; כולל גופנים, מנוע וסידור התצוגה |

בדיקת ההקלדה נפרדת מהחותמת האחרונה: מקלדת CDP, המתנה מוגבלת עד שהמודל והפסקה המוצגת מכילים בדיוק את הטקסט הצפוי, ואימות חוזר אחרי שני פריימים. אין כאן מדידת זמן עד צבע בפיקסלים או טענה שהסרת splash מוכיחה מוכנות לעריכה.

`worker.sourceBytes` הוא גודל קוד ה־worker בפועל לפני escaping בתוך הבאנדל. `constructorMs` מודד את קריאת `new Worker` הסינכרונית בלבד; `firstResponseMs` כולל גם קומפילציה, עיבוד והודעה ראשונה. קלט ריק משמש לכיול עלות ההקמה וההודעות. `--baseline-dist /path/to/baseline/dist` מוסיף גדלים ו־SHA-256 של שני קובצי `app.js` ואת ההפרש הכולל; אין לחבר את `sourceBytes` שוב להפרש, כי הוא כבר כלול בבאנדל.

ברירת המחדל היא 5,000 פסקאות ושלוש חזרות לעיבוד החבילה. אפשר לשנות `--paragraphs`, `--runs`, `--port`. `--cpu` מאט את renderer בבדיקת החבילה בלבד; הוא אינו מדמה מחשב חלש באופן מלא. בדיקת הפתיחה המלאה משתמשת ב־100 פסקאות, חזרה אחת לכל מסלול וקצב CPU רגיל; הבסיס הוא אותו build עם התאוששות מקומית כפויה. זהו שער תפקודי ואומדן ראשוני, לא השוואת Release לפני/אחרי.

אין סף זמן שמכשיל בדיקות: העברה ל־worker נועדה לשחרר את הממשק, ויכולה להאריך זמן כולל בגלל הקמה והעברת הודעות. יש לחזור על מטריצת הפתיחה וההקלדה במדידת Release בתוך אוצריא, לרבות DOCM אמיתי ומחשב חלש. אין להסיק מתוצאות headless על זמני IPC, דיסק או ציור native.
